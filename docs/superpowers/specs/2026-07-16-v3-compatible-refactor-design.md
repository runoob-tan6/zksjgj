# 钻孔数据编辑工具 v3 兼容重构设计

## 1. 决策与范围

`v3` 从当前 `v2/` 完整复制后独立演进。此前 `codex/v3-refactor` 分支中的三栏工作台方案不再作为交付基础，保留该分支仅用于历史追溯。

本次允许改变的可见内容仅限版本标识：窗口标题、包版本、启动命令、打包配置和 EXE 名称从 v2 更新为 v3。其他布局、尺寸、菜单、标签页、按钮、提示文字、快捷键、上下文菜单、选择流程、保存流程、导入导出流程和正常业务结果必须与 v2 一致。

允许修复明确缺陷，包括崩溃、数据丢失、保存不完整、后台任务失控和无效输入导致的异常。修复不得增加新的操作步骤或改变正常路径的使用习惯。

## 2. 方案比较

### 方案 A：复制后渐进式兼容重构（采用）

先复制 v2，再用特征测试锁定现状，逐个抽离非 UI 职责。每次重构都运行 v2/v3 对照测试。该方案最容易证明没有遗漏功能，也能持续降低主窗口、文件写入和后台任务的风险。

### 方案 B：仅复制并做局部清理

风险最低、交付最快，但无法有效改善约 1300 行主窗口的职责集中、重复保存逻辑和测试缺口，长期维护收益有限。

### 方案 C：复用旧三栏 v3 的后端并移植 v2 UI

已有代码较多，但领域模型、控制器和保存语义已经偏离 v2，重新接回 v2 UI 容易产生隐藏行为差异，不符合兼容性优先原则。

## 3. 版本隔离

- 新实现位于独立 `v3/`，运行时不导入 `v2/`。
- 开始前生成 `v2/` 全文件的路径、大小和 SHA-256 基线；结束时重新比较。
- 不修改、删除、格式化或向 `v2/` 新增任何文件。
- 测试 v2 时禁用字节码和 pytest 缓存，并把临时目录放到系统临时目录。
- v3 使用独立分支和工作树开发，不覆盖现有三栏 v3 分支。

## 4. 兼容基线

在重构前建立以下可自动重复验证的基线：

1. **功能清单**：记录文件菜单、编辑菜单、工具菜单、快捷键、标签页、树节点与上下文菜单、拖放导入、保存确认、关闭确认、校验和导出入口。
2. **UI 结构**：记录窗口标题以外的窗口尺寸、分栏结构、控件层级、对象类型、可见文字、标签页顺序和关键控件几何位置。
3. **交互行为**：覆盖项目加载、选择切换、字段编辑、表格增删、撤销恢复、钻孔和剖面增删复制、附属文件操作、保存、校验、导入、导出和关闭确认。
4. **文件行为**：覆盖主文件、`.-b/c/d/g/h`、全部试验后缀、剖面文件、项目配置文件、额外文件、编码、换行和备份。
5. **视觉对照**：使用相同 Qt 环境和固定数据分别渲染 v2/v3 关键页面，遮盖版本标题后进行像素差异检查。

当前 v2 自动化基线为 31 个测试通过并带 2 个 pytest 收集警告。v3 应保留这些测试所覆盖的行为，并消除警告。

## 5. 架构

v3 保留 v2 的 `domain`、`application`、`infrastructure` 和 `ui` 分层及 `borehole` 包名，以减少导入和运行差异。优化集中在现有边界内部，不重做用户界面。

### 5.1 UI 层

`MainWindow` 的构造顺序、控件树、信号入口和用户可见结果保持不变。把后台线程封装、保存编排、项目结构变更和纯状态计算移到独立模块后，原有槽方法仍作为兼容门面调用这些服务。

UI 页面只做以下内部优化：减少重复刷新、阻断加载期间的无意义信号、复用表格更新逻辑、保证活动编辑器在切换和保存前提交。不得调整布局参数、控件类型或显示文字。

### 5.2 应用层

新增小型服务以承接以下职责：

- 项目和当前选择状态的查询与变更。
- 保存前收集脏对象并生成保存计划。
- 钻孔、剖面和项目配置文件的新增、复制、删除与重命名操作。
- 后台任务的开始、成功、失败和清理生命周期。

服务使用现有领域模型，返回适合现有 UI 提示的数据，不引入新的用户概念。

### 5.3 基础设施层

保留 v2 的解析和输出格式。文件保存改为可测试的事务：先生成目标内容，写同目录临时文件，备份原文件，再执行原子替换；失败时恢复已替换文件并保留脏状态。

导入导出和标贯分析只做重复计算消除、输入边界检查和异常归一化。输出字段、工作表、公式、CSV 列和排序保持一致。

### 5.4 领域层

保持数据类字段和校验消息不变。只允许加入不改变结果的类型收窄、纯函数提取、自然排序缓存和显式有限数检查。所有修复必须先有失败测试。

## 6. 数据流与错误处理

正常编辑数据流保持：UI 编辑器更新现有领域对象，标记对应脏状态，撤销管理器记录快照，保存按钮展示原确认框并在后台执行写入，完成后按原方式刷新树和状态栏。

后台任务必须保证：同一时间只有一个冲突任务；无论成功或失败都恢复菜单状态并释放线程；异常转换为原有中文错误框；关闭窗口时不遗留运行线程。

保存失败必须保证：原文件可恢复、未成功的删除不生效、模型仍为未保存、错误包含具体文件与操作。正常保存的提示文字和文件集合保持 v2 行为。

## 7. 测试策略

采用测试驱动的短循环：先写一个能在待优化代码上失败或能锁定既有行为的测试，确认失败原因，再做最小改动并运行全量回归。

- 单元测试：领域模型、校验、撤销、保存计划、事务、编码、导入导出纯逻辑。
- 集成测试：合成项目的加载、编辑、保存、重载、备份与故障回滚。
- UI 测试：菜单、标签页、快捷键、树操作、表格编辑、对话框调用和忙碌状态。
- 对照测试：从同一测试数据分别收集 v2/v3 UI 清单、输出文件和截图，除版本标识外必须一致。
- 发布测试：开发入口可启动、PyInstaller 构建成功、EXE 启动后出现主窗口且无立即崩溃。

## 8. 性能目标

性能优化不设置会改变交互的激进目标。对包含大量钻孔和试验记录的合成项目记录加载、列表刷新、校验和导出基线；优化后不得退化，并优先降低重复扫描、重复排序、重复模型刷新和重复 Excel 样式计算。

性能测试使用宽松但可重复的相对阈值，避免把机器瞬时负载当作产品缺陷。

## 9. 交付物

`v3/` 包含独立源码、测试、`pyproject.toml`、开发启动入口、v3 打包配置、打包脚本、README、v2 哈希基线和兼容性报告。构建产物不提交源码仓库，但在本机完成构建与启动验证。

## 10. 验收条件

1. v3 的窗口标题和发布名称显示 v3，其余关键 UI 对照一致。
2. v2 功能清单中的每一项都有 v3 实现和自动化或明确的人工验证记录。
3. v2/v3 对同一输入的保存、导入、导出和分析结果一致，已批准缺陷修复单独记录。
4. v3 全量 pytest、Ruff 和 mypy 通过且无警告。
5. 事务失败测试证明不会造成原文件丢失或错误清除脏状态。
6. Windows EXE 构建和启动冒烟测试通过。
7. v2 实施前后 SHA-256 清单完全一致。

## 11. 用户授权

用户已确认：v3 以完整复制 v2 后仅优化内部代码、性能、稳定性和测试为准；旧三栏实现不采用；版本标识改为 v3；允许修复明确缺陷；后续实现细节由工程判断直接推进，无需逐项询问。
